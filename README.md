# Since Us

Мобильное пространство для двоих на React и TypeScript: дни вместе, памятные фотографии, даты, планы, чат, аккаунты и профили. Мягкая палитра и стеклянные поверхности вдохновлены iOS Liquid Glass.

## Запуск

Нужен Node.js 24.12+ с npm (сервер использует встроенный SQLite).

```sh
npm install
npm run dev -- --port 8000 --strictPort
```

Откройте http://localhost:8000 для проверки экрана входа. Полный вход требует открытия Mini App через Telegram-бота по публичному HTTPS-адресу: обычный браузер не выдаёт проверенные данные Telegram. Фронтенд и API обслуживаются одним процессом, отдельный запуск базы не нужен.

```sh
npm run build
npm run preview -- --port 8000 --strictPort
```

Перед запуском preview остановите dev на том же порту. Папка dist содержит фронтенд; для работы аккаунтов также нужны сервер из server/api.mjs и SQLite. Простая публикация dist на статическом хостинге не подключает API.

## Railway

Railway использует `npm run build` для сборки и `npm start` для запуска приложения на порту `PORT`. Node.js 24.12 или новее нужен встроенной SQLite.

Добавьте в Variables сервиса `TELEGRAM_BOT_TOKEN` и `COOKIE_SECURE=true`, затем включите публичный HTTPS-домен в Networking. Сервер возьмёт его из `RAILWAY_PUBLIC_DOMAIN`, зарегистрирует Telegram webhook и настроит кнопку меню. Если используете собственный домен, задайте `WEB_APP_URL=https://ваш-домен`. Один Railway-сервис обслуживает и приложение, и бота. Если база должна переживать перезапуски и новые деплои, подключите Railway Volume с путём `/app/storage`; приложение автоматически сохраняет базу в этот каталог. Либо укажите `DATABASE_PATH=/app/storage/blizhe.sqlite`. Настройте Railway healthcheck на `/api/health`.

Файл `.env.example` содержит шаблон локальных переменных. Не загружайте `.env` с реальным токеном в GitHub.

## Первый вход и работа пары

1. Откройте приложение кнопкой в Telegram-боте. Сервер проверит подпись Telegram и автоматически создаст личное пространство при первом входе. Почта и пароль не нужны.
2. Откройте профиль через аватарку в верхнем углу. Фото автоматически берётся из Telegram; там же укажите день рождения, описание и дату начала отношений.
3. В разделе пары создайте приглашение и передайте код партнёру. Он открывает приложение через бота и вводит код в настройках. Код действует 24 часа; в паре может быть два человека.
4. Даты, планы, фото и сообщения общие. Изменения второго участника появляются автоматически, примерно раз в 6 секунд при открытом приложении. При одновременном изменении приложение просит повторить действие, не перезаписывая свежие данные.

Каждый редактирует свой профиль. Отправитель сообщений определяется вошедшим Telegram-аккаунтом. Для присоединения по приглашению личное пространство должно быть пустым: существующая история не переносится автоматически. В настройках можно скачать резервную копию истории.

## Данные

Telegram-аккаунты, сессии, профили и общая история хранятся в storage/blizhe.sqlite на компьютере с сервером. SQLite использует WAL: для файлового резервирования сначала остановите приложение и скопируйте всю папку storage. Эта папка исключена из Git и закрыта для прямого скачивания через Vite. Фотографии сжимаются браузером перед сохранением. В интерфейсе нет автоматического переноса старых демонстрационных данных из localStorage; существующие данные браузера не удаляются.

Сессия хранится в HttpOnly-cookie на 30 дней. Telegram-подпись и срок действия данных входа проверяются на сервере; токены сессий хранятся в хешированном виде. Есть проверка входящих данных, изоляция пространств и ограничение попыток входа. Для публикации в интернете необходим HTTPS и COOKIE_SECURE=true; HTTP по домашней сети предназначен для локальной проверки. Старые аккаунты с почтой сохранены в базе для совместимости, но форма входа по почте убрана из интерфейса.

## PWA

Установка на экран телефона доступна у готовой сборки через HTTPS. На iPhone: Safari → «Поделиться» → «На экран Домой». На Android: установка через меню браузера. Service worker кеширует только оболочку и статические ресурсы, не запросы API. Вход, загрузка личных данных и сохранение требуют соединения с сервером. В режиме разработки service worker не регистрируется.

## Telegram Mini App

Приложение можно открыть внутри Telegram. Скопируйте `.env.example` в `.env`, добавьте токен своего бота из @BotFather в `TELEGRAM_BOT_TOKEN` и оставьте `COOKIE_SECURE=true` для HTTPS. После изменения `.env` перезапустите сервер. Токен используется только сервером и не попадает в браузер.

1. Запустите приложение и откройте его по публичному HTTPS-адресу Railway либо через Cloudflare Tunnel.
2. В @BotFather откройте `/mybots` → выберите бота → **Bot Settings → Configure Mini App → Enable Mini App**. Укажите публичный HTTPS-адрес приложения.
3. После деплоя отправьте боту `/start`: он должен ответить кнопкой открытия приложения. Кнопка меню настраивается сервером автоматически. Если бот не отвечает, проверьте Deploy Logs: там будет видно, отсутствует ли токен/домен или Telegram отклонил webhook.

Первый вход через бота создаёт аккаунт автоматически. Если браузер уже хранит сессию прежнего аккаунта, он привязывается к Telegram и сохраняет историю. Последующие открытия Mini App входят автоматически. Подпись Telegram и срок действия `initData` проверяет сервер. В Mini App работают оформление с учётом Telegram-темы, системные безопасные отступы и кнопка «Назад».

Cloudflare Quick Tunnel выдаёт временный адрес. Если адрес изменился, обновите URL Mini App в BotFather. Для постоянного адреса используйте именованный туннель или HTTPS-хостинг.

## Серверные операции с записями

Фронтенд сохраняет одиночные изменения через отдельные маршруты `/api/books`, `/api/memories`, `/api/dates`, `/api/plans`.

- `GET /api/<resource>?limit=20&offset=0` — список с `items`, `total`, `nextOffset`, `revision`. Максимальный размер страницы — 100. Для моментов доступен `bookId`; порядок — от ранних дат к поздним, при одинаковой дате по ID.
- `GET /api/<resource>/<id>` — одна запись и версия пространства.
- `POST /api/<resource>` — создать запись: `{ "revision": 5, "item": { ... } }`. ID можно передать или получить с сервера.
- `PATCH /api/<resource>/<id>` — изменить указанные поля: `{ "revision": 6, "item": { "title": "Новое название" } }`. Неизменённую фотографию отправлять не нужно.
- `DELETE /api/<resource>/<id>` — удалить: `{ "revision": 7 }`. Книгу с моментами и последнюю книгу удалить нельзя. Автоматические годовщина и дни рождения изменяются через настройки.
- `GET /api/sync` — только `spaceId` и `revision`. Фронтенд проверяет версию каждые 6 секунд, пока приложение видно; полная история скачивается только при изменениях.

Все маршруты требуют существующую HttpOnly-сессию. Пространство определяется сервером по вошедшему пользователю. Для изменений нужны JSON и заголовок `X-Blizhe-Client: 1`; проверяется источник запроса. Ответ изменения содержит только `revision` и `item` либо `deletedId`. Устаревшая версия даёт 409 без записи изменений, отсутствующая запись — 404. Сохранение выполняется условным UPDATE по ID пространства и его версии. Старый `/api/data` сохранён для совместимости и операций, изменяющих несколько разделов сразу.

### Следующие этапы бэкенда

Текущий этап уменьшает сетевой трафик, но хранение пока остаётся SQLite с общей JSON-записью пространства и фотографиями внутри неё. Постраничный API сейчас ограничивает ответ, а не чтение базы. Готовность к десяткам тысяч пользователей пока не проверена; запускать несколько копий сервера с разными локальными базами нельзя.

1. Добавить PostgreSQL и отдельные таблицы пользователей, пар, участников, книг, моментов, дат и планов. Написать и проверить миграцию существующей SQLite-базы с сохранением идентификаторов и принадлежности записей. Индексы для моментов: пространство, книга, дата и ID.
2. Перенести изображения в приватное S3-совместимое хранилище. В базе оставить метаданные и ключ объекта. Проверять размер и тип на сервере; доступ выдавать только участникам пары. Перенести старые base64-фото с проверкой количества и целостности.
3. Заменить общую версию пространства версиями записей; добавить журнал изменений и загрузку только изменений с последнего курсора. Тогда независимые изменения партнёров не будут конфликтовать.
4. Вынести уведомления и обработку изображений в очередь фоновых заданий; хранить ограничители запросов и дедупликацию webhook в общем хранилище для нескольких серверов.
5. До увеличения нагрузки настроить восстановление из резервной копии, метрики, ошибки и нагрузочные проверки по числу одновременно активных пользователей, объёму фото и частоте изменений. PostgreSQL и хранилище подключать через переменные окружения только после реализации и проверки миграции.
